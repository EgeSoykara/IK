# Phase 1 Architecture

## Scope
Phase 1 establishes the domain and data authority for the HR Personnel Registry and Leave Module. It does not implement real LDAP / Active Directory login or final AD group to application role mapping.

## Locked Decisions
- EF Core is the application data access authority.
- MSSQL is the database target.
- Leave rights renew every year.
- Each leave type carries its own `AnnualQuota`, `CarryOverRule`, and `MaxAccrualDays` values aligned to the MSSQL data model expectation.
- Previous-year remaining leave can be carried into the new year when the leave type's `CarryOverRule` is enabled.
- A 50-day accumulation limit is a warning and confirmation rule, not a hard cap.
- If the warning is confirmed, carry-over can continue.
- Leave approval flows from the employee's manager to Human Resources final approval.
- Leave requests use date-only periods. Requested days count Monday through Friday and exclude Saturdays, Sundays, and configured public holidays.
- Half-day leave is an explicit request choice, is valid only for one weekday, and deducts `0.5` day.
- Human Resources is the final approval authority.
- Regional senior management means the region manager or a higher manager in that manager chain.
- The identity field display name is "KKTC Kimlik No".
- An authenticated employee may upload only their own profile photo and documents. Cross-employee dashboard visibility never elevates file-upload or file-download ownership.
- Employee file bytes stay outside `wwwroot`; authorized endpoints resolve them through DB metadata and canonical storage keys.
- Documents use a DB-backed category canonical key from their first release. The seeded `identity`, `employment`, `education`, `health`, and `other` categories each map to their own folder, and later categories are data additions rather than schema changes.

## Code Authority
- `Database/HumanResourcesDbContext.cs` is the EF Core DbContext authority.
- `Models/*` contains the Phase 1 data contract and enum authority.
- `Models/LeaveType.cs` defines whether a leave type can carry prior-year days into the next year through `CarryOverRule`.
- `Services/LeaveBalanceService.cs` owns annual renewal, applies the selected leave type's `AnnualQuota`, and enforces carry-over plus 50-day warning confirmation behavior.
- `Services/LeaveRequestService.cs` owns leave request creation, update, workday-aware overlap checks, manager approval, HR final approval, rejection reasons, and balance update on approval. It obtains the applicable configured holiday dates from `PublicHolidayCalendar` before every calculation. Manager and Human Resources approvals recalculate requested working days against the current calendar, so a holiday configured before final approval is excluded; already-approved requests and balances are not rewritten retroactively. Date ranges that intersect only on weekends or configured holidays do not conflict.
- `Services/LeaveDayCalculator.cs` is the single requested-day calculation authority: it counts only Monday through Friday in the inclusive selected date range, excludes the supplied configured public-holiday dates, rejects ranges with no working day, and returns `0.5` only for an explicitly selected half-day on one eligible working day.
- `Models/PublicHoliday.cs` owns the unique date and required display name for a public holiday. `Services/PublicHolidayCalendar.cs` owns the range-scoped database read used by leave calculations. `Components/Pages/PublicHolidays.razor` is the year-based operator surface; Administrator and Human Resources roles receive `CanManagePublicHolidays`, while ordinary employees cannot access or mutate the calendar. Create, update, and delete operations are audited.
- `Services/LeaveApprovalVisibilityQuery.cs` owns the single approval-row visibility scope used by approval table reads, filter-option reads, and approval deletion lookups: Human Resources principals see HR-role approvals, while manager principals see only manager-role approvals assigned to their employee ID.
- `Services/LeaveApprovalFilterOptionQuery.cs` projects requester, leave-type, and approver autocomplete values from that visibility scope with SQL-side `Distinct` and ordering so page initialization loads only unique authorized options rather than the full approval history.
- `Services/AuditLogPageService.cs` owns server-side audit log pagination for read-only audit log browsing.
- `Services/ManagementTablePageQuery.cs` owns the shared MudBlazor server-side table page projection used by management pages: it normalizes page inputs, counts the filtered query before paging, and applies the requested `Skip` / `Take` slice after each page has supplied its own visibility, search, relationship include, and deterministic ordering rules.
- `Services/ManagementAuthorizationService.cs` owns manager-chain traversal helpers for region-manager-or-above authorization decisions.
- `Services/AuditLogService.cs` owns audit log creation in Phase 1 service flows.
- `Models/EmployeeProfilePhoto.cs`, `Models/EmployeeDocument.cs`, and `Models/EmployeeDocumentCategory.cs` own employee-file metadata. `EmployeeDocument` keeps the existing employee/category metadata and adds nullable restrictive composite foreign keys from `(EmployeeId, related record id)` to exactly one identity, education, or course/certificate record for new uploads. The composite keys make cross-employee links impossible even for direct database writes; all-null remains valid only for preserved legacy documents whose related record cannot be determined safely. `EmployeeDocumentCategory.CanonicalKey` remains the stable storage-folder segment; original file names are display/download metadata only and never storage paths.
- `Models/EmployeeBankAccount.cs`, `Models/EmployeeIdentityDocument.cs`, `Models/EmployeePhone.cs`, `Models/EmployeeAddress.cs`, `Models/EmployeeEducation.cs`, and `Models/EmployeeCourseCertificate.cs` own the structured multi-row personnel information that was absent from the core employee record. `Models/EmployeeTermination.cs` owns the single structured termination record per employee. These entities use attribute-first mapping and restrictive employee foreign keys; they do not duplicate `Employee.SicilNo`, `KktcKimlikNo`, `DepartmentId`, `ManagerId`, `StartDate`, or `Status`. Bank, phone, and address each permit at most one `IsPrimary = 1` row per employee through SQL Server filtered unique indexes. Because data annotations cannot express filtered indexes, those three indexes are the only personnel-mapping Fluent exceptions in `HumanResourcesDbContext.OnModelCreating`.
- `Services/EmployeeFileService.cs` is the single profile-photo and document operation authority. It accepts an explicit target employee, authorizes that target through `PageAccessService`, verifies that every new document belongs to an identity, education, or course/certificate row owned by the same employee, validates file size, extension and signature, persists file metadata, records upload audit events, and replaces the previous profile photo. Employees are restricted to their own target ID; `CanCreateNewEmployee` is the only cross-employee file elevation. Profile-photo metadata uses SQL Server `rowversion`, so concurrent replacements cannot leave a losing metadata write as a second authority.
- `Services/EmployeeFileCanonicalKey.cs` owns canonical paths under `employees/{zero-padded employee id}/profile-photo/` and `employees/{zero-padded employee id}/documents/{category canonical key}/`. `Services/LocalEmployeeFileStore.cs` owns traversal-safe local-folder I/O behind `IEmployeeFileStore`; writes use a temporary sibling plus atomic rename so final keys never expose partial bytes. Its default root is the git-ignored `App_Data/employee-files` folder, `EmployeeFiles:RootPath` may point to an operator-managed volume, and startup rejects a root equal to or beneath `wwwroot`.
- `Program.cs` owns ASP.NET Core cookie authentication registration, the `/auth/login` and `/auth/logout` endpoints, and the authenticated `/employee-files/profile-photo/{employeeId}` plus `/employee-files/documents/{documentId}` read endpoints. `EmployeeFileService` applies own-or-elevated authorization before storage is opened.
- `Services/PageAccessService.cs` owns authenticated page access decisions, reads signed-in authorization from the routed `ClaimsPrincipal`, owns principal-only shell access for the signed-in user's own dashboard context, and owns every permission-based elevation beyond that baseline. It also owns the clean-database bootstrap rule for the local `Departments` and `Employees` pages.
- `Services/PageAccessService.CanAccessPersonnelInformation` and `CanEditPersonnelInformation` are the backend authorities for common structured bank, identity/document, phone, address, education, course/certificate, profile-photo, and general-information routes. An authenticated principal with an employee claim may access and mutate only that employee's permitted records; `CanCreateNewEmployee` elevates the principal to select and manage other employees. `CanManageEmployeeTerminations` separately requires that elevation, so termination data is neither queried nor rendered for ordinary employees. Employee-search permission alone grants no structured-personnel access, and navbar visibility is never the security boundary.

## Data Flow
1. HR or an authorized manager creates or renews a leave balance through `LeaveBalanceService`.
2. The service uses the selected leave type's `AnnualQuota` as the renewed `EntitledDays`.
3. The service calculates carry-over from the previous year's remaining balance when renewing when `CarryOverRule` is enabled.
4. If entitlement plus carry-over exceeds 50 days, the service returns a confirmation-required result without saving.
5. If the caller confirms the warning, the service saves the balance without capping the value.
6. An employee selects a date range and optional half-day through the leave-request form; Saturdays and Sundays are excluded from the displayed requested-day result.
7. Before submission, the form confirms how many working days will be deducted if the request receives final approval, then creates the request through `LeaveRequestService`.
8. The request is blocked if its range has no working day, half-day spans more than one date, the employee has no manager, the employee has insufficient balance, or the employee has an overlapping active or approved request.
9. Only the assigned manager approves or rejects the first approval step.
10. Human Resources approves or rejects the final step.
11. Only final HR approval changes the used and remaining leave balance by the already-calculated working-day amount, including `0.5` for half-day requests.
12. Rejection does not change the leave balance and must include a reason.
13. Cross-year leave requests are rejected in Phase 1 so yearly balance semantics stay unambiguous.
14. `Genel Bilgiler` submits a profile photo for the selected authorized employee; identity, education, and course/certificate dialogs submit a file together with the selected related-record ID.
15. `EmployeeFileService` authorizes the target employee, verifies related-record ownership, validates file content, creates an opaque canonical storage key, atomically writes bytes outside `wwwroot`, then commits metadata and an audit event through a fresh operation context. A failed or cancelled metadata commit performs non-cancelled file compensation.
16. Replacing a profile photo commits the new metadata before removing the superseded file; each new document stores exactly one related-record FK while preserved ambiguous legacy documents retain all-null related-record FKs.
17. Authenticated download endpoints authorize the document/photo owner or elevated manager before opening the canonical storage key; user-supplied names never participate in path resolution.
