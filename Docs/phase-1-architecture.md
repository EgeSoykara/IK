# Phase 1 Architecture

## Scope
Phase 1 establishes the domain and data authority for the HR Personnel Registry and Leave Module. It does not implement real LDAP / Active Directory login or final AD group to application role mapping.

## Locked Decisions
- EF Core is the application data access authority.
- MSSQL is the database target.
- Leave rights renew every year.
- Current-year automatic rights are reconciled idempotently on application startup and every local day through a hosted worker; new hires are included on `StartDate` without waiting for January 1.
- Each leave type carries its own `AnnualQuota`, `CarryOverRule`, and `MaxAccrualDays` values aligned to the MSSQL data model expectation.
- The five original seeded leave types start at 30 days. Service-tier leave carries over, sickness and pregnancy do not, every original type retains the 50-day warning, and 30+ years remains in the top service tier. Mobilization leave is a separate male-only, non-carrying entitlement with a hard two-day limit that cannot be bypassed by the general over-limit confirmation.
- Previous-year remaining leave can be carried into the new year when the leave type's `CarryOverRule` is enabled.
- A 50-day accumulation limit is a warning and confirmation rule, not a hard cap.
- If the warning is confirmed, carry-over can continue.
- Leave approval flows from the employee's manager to Human Resources final approval.
- Leave requests use date-only periods. Requested days count Monday through Friday and exclude Saturdays, Sundays, and configured public holidays.
- Half-day leave is an explicit request choice, is valid only for one weekday, and deducts `0.5` day.
- Every persisted leave amount is a non-negative whole or half day. Automatic calendar-day proration rounds down to a whole day.
- Employees request Annual Leave as the aggregate of the three service-tier balances, or any persisted non-service leave type for which they have a positive balance and remain eligible. Annual Leave consumes carry-over before entitlement; a specific type consumes only its selected balance.
- Pregnancy leave is female-only and manual; it is never assigned by the automatic worker.
- Human Resources is the final approval authority.
- Regional senior management means the region manager or a higher manager in that manager chain.
- The identity field display name is "KKTC Kimlik No".
- An authenticated employee may upload only their own profile photo and documents. Cross-employee dashboard visibility never elevates file-upload or file-download ownership.
- Employee file bytes stay outside `wwwroot`; authorized endpoints resolve them through DB metadata and canonical storage keys.
- Documents use a DB-backed category canonical key from their first release. The seeded `identity`, `employment`, `education`, `health`, and `other` categories each map to their own folder, and later categories are data additions rather than schema changes.

## Code Authority
- `Database/HumanResourcesDbContext.cs` is the EF Core DbContext authority.
- `Models/*` contains the Phase 1 data contract and enum authority.
- `Models/LeaveType.cs` defines quota, carry-over, warning, and the immutable automatic eligibility kind. `LeaveTypes` is the persisted policy authority; `/LeaveTypes` edits its operator-controlled values, subject to the hard male-mobilization policy check of no carry-over and at most two days.
- `Services/LeaveEntitlementService.cs` owns `StartDate`-based service-year eligibility and calendar-day 10/20-year transition proration. It floors each prorated tier to a whole day, fails closed on missing start dates, keeps 30+ years in the 20-year-plus tier, and excludes pregnancy from automatic assignment.
- `Services/LeaveBalanceService.cs` owns authorized person/department/all assignment, entitled/carry-over/used-day corrections, delete mutations, daily idempotent reconciliation, transaction boundaries, carry-over, 50-day warning records, the non-overridable two-day Mobilization balance limit, and audit creation. `LeaveBalance.UsedDays` is the current corrected usage and capacity authority; source allocations remain immutable approval provenance and do not constrain current entitlement/carry-over capacity after an audited correction. Service-tier leave types form one carry-over group, so a tier transition transfers the prior service-tier remainder once to the first eligible tier instead of stranding or duplicating it.
- `Services/DailyLeaveEntitlementWorker.cs` owns startup catch-up and next-local-midnight scheduling. It creates or updates current-year automatic balances, includes a new hire on their start date, retries failed runs, and can be disabled through `DailyLeaveEntitlementWorker__Enabled`.
- `Services/LeaveCarryOverWarningService.cs` is the backend authorization and acknowledgement authority for `/LeaveCarryOverWarnings`; warnings expose carried, entitled, total and limit days without capping the balance.
- `Services/LeaveRequestService.cs` owns leave request creation, update, explicit retrospective-request persistence, workday-aware overlap checks, manager approval, HR final approval, rejection reasons, category aggregation, and persisted source allocation on approval. Normal requests reject past dates; `IsRetrospective` is the single explicit opt-in that permits them without bypassing any approval, balance, overlap, or calendar rule. It obtains the applicable configured holiday dates from `PublicHolidayCalendar` before every calculation. Manager and Human Resources approvals recalculate requested working days against the current calendar, so a holiday configured before final approval is excluded; already-approved requests and balances are not rewritten retroactively. Date ranges that intersect only on weekends or configured holidays do not conflict. Annual approval consumes all carry-over first and then entitlement in 0-10, 10-20, 20-plus tier order.
- `Services/LeaveCancellationService.cs` is the single leave-cancellation mutation authority. It permits owner-scoped or established elevated-editor direct cancellation only while the original request still awaits its manager, persists the actual initiating employee/display identity, and exposes the terminal outcome in decision history; after manager approval, the original HR decision must finish before an approved request can create a manager → HR cancellation workflow. Cancellation requests own an inclusive `CancellationStartDate`–`CancellationEndDate`, including a same-day range, and reject overlap with another active or approved cancellation. Final leave approval persists the exact date/amount allocation in `LeaveRequestApprovedDays`; cancellation refund sums only those approval-time dates inside the selected range, so later public-holiday changes cannot alter the refund. HR cancellation approval reverses the amount from current `UsedDays`, removes the selected active-day rows, and records immutable balance/source refund provenance. Full cancellation marks the original request cancelled; partial or middle cancellation preserves its original boundaries and reduces only its requested-day amount. Tracking and overlap reads use the same remaining approved-day authority; delegation pauses for approved cancellation ranges. `LeaveCancellationRequests`, `LeaveCancellationApprovals`, `LeaveCancellationBalanceRefunds`, and `LeaveRequestApprovedDays` are the durable workflow, decision-history, refund, and active-day contracts.
- `Services/LeaveDayCalculator.cs` is the single requested-day calculation authority: it counts only Monday through Friday in the inclusive selected date range, excludes the supplied configured public-holiday dates, rejects ranges with no working day, and returns `0.5` only for an explicitly selected half-day on one eligible working day.
- `Models/PublicHoliday.cs` owns the unique date and required display name for a public holiday. `Services/PublicHolidayCalendar.cs` owns the range-scoped database read used by leave calculations. `Components/Pages/PublicHolidays.razor` is the year-based operator surface; Administrator and Human Resources roles receive `CanManagePublicHolidays`, while ordinary employees cannot access or mutate the calendar. Create, update, and delete operations are audited.
- `Services/LeaveApprovalVisibilityQuery.cs` owns the single approval-row visibility scope used by approval table reads, filter-option reads, and approval deletion lookups: Human Resources principals see HR-role approvals, while manager principals see only manager-role approvals assigned to their employee ID.
- `Services/LeaveApprovalFilterOptionQuery.cs` projects requester, approver, and visible leave-type autocomplete values from that visibility scope with SQL-side `Distinct` and ordering so page initialization loads only unique authorized options rather than the full approval history.
- `Services/AuditLogPageService.cs` owns server-side audit log search and pagination. An authorized but empty search returns no rows, so `/AuditLogs` never loads the full history automatically; the exact `ActorEmployeeId` selected from the employee-name/surname/sicil autocomplete, action, local date range, and detail criteria are applied before count and paging. Suggestions are limited to employees referenced by audit history, return at most 20 values, and do not share a DbContext with table loads. Display names are resolved from the current employee record; deleted employees remain attributable as `Silinmiş çalışan (#ID)`. `Services/AuditLogPresentation.cs` translates stored technical key/value details into plain Turkish labels and readable values without changing immutable audit data.
- `Services/EmployeeTerminationService.cs` is the single read and mutation authority for the Management `/EmployeeTerminations` module. Every table, filter-option, autocomplete, detail, create, update, and delete operation rechecks `CanManageEmployeeTerminations` and creates its own DbContext. Create/update mark the employee passive; delete intentionally preserves employee status. All three mutations use the employee's existing `RowVersion` as the termination-lifecycle concurrency token and write their distinct immutable audit action in the same `SaveChanges` transaction.
- `Services/ManagementTablePageQuery.cs` owns the shared MudBlazor server-side table page projection used by management pages: it normalizes page inputs, counts the filtered query before paging, and applies the requested `Skip` / `Take` slice after each page has supplied its own visibility, search, relationship include, and deterministic ordering rules.
- `Services/ManagementAuthorizationService.cs` owns manager-chain traversal helpers for region-manager-or-above authorization decisions.
- `Services/AuditLogService.cs` owns audit log creation in Phase 1 service flows. Human actions require the authenticated employee claim as `ActorEmployeeId`; usernames are not accepted or retained as audit authority. Background work uses the mutually exclusive `SystemActorKey`. Audit actors intentionally have no employee foreign key so employee deletion cannot erase or invalidate immutable history; the database check constraint requires exactly one actor kind.
- `Models/EmployeeProfilePhoto.cs`, `Models/EmployeeDocument.cs`, and `Models/EmployeeDocumentCategory.cs` own employee-file metadata. `EmployeeDocument` keeps the existing employee/category metadata and adds nullable restrictive composite foreign keys from `(EmployeeId, related record id)` to exactly one identity, education, or course/certificate record for new uploads. The composite keys make cross-employee links impossible even for direct database writes; all-null remains valid only for preserved legacy documents whose related record cannot be determined safely. `EmployeeDocumentCategory.CanonicalKey` remains the stable storage-folder segment; original file names are display/download metadata only and never storage paths.
- `Models/EmployeeBankAccount.cs`, `Models/EmployeeIdentityDocument.cs`, `Models/EmployeePhone.cs`, `Models/EmployeeAddress.cs`, `Models/EmployeeEducation.cs`, and `Models/EmployeeCourseCertificate.cs` own the structured multi-row personnel information that was absent from the core employee record. `Models/EmployeeTermination.cs` owns the single structured termination record per employee. These entities use attribute-first mapping and restrictive employee foreign keys; they do not duplicate `Employee.SicilNo`, `KktcKimlikNo`, `DepartmentId`, `ManagerId`, `StartDate`, or `Status`. Bank, phone, and address each permit at most one `IsPrimary = 1` row per employee through SQL Server filtered unique indexes. Because data annotations cannot express filtered indexes, those three indexes are the only personnel-mapping Fluent exceptions in `HumanResourcesDbContext.OnModelCreating`.
- `Services/EmployeeFileService.cs` is the single profile-photo and document operation authority. It accepts an explicit target employee, authorizes that target through `PersonnelAuthorizationService`, verifies that every new document belongs to an identity, education, or course/certificate row owned by the same employee, validates file size, extension and signature, persists file metadata, records upload audit events, and replaces the previous profile photo. Every preview/download is reauthorized immediately before storage opens and commits a distinct viewed/downloaded audit event before returning content; an audit-write failure closes access. Own-employee access is full, department responsibility permits education/certificate preview only, and global preview/download remain separate database permissions. Profile-photo metadata uses SQL Server `rowversion`, so concurrent replacements cannot leave a losing metadata write as a second authority.
- `Services/EmployeeFileCanonicalKey.cs` owns canonical paths under `employees/{zero-padded employee id}/profile-photo/` and `employees/{zero-padded employee id}/documents/{category canonical key}/`. `Services/LocalEmployeeFileStore.cs` owns traversal-safe local-folder I/O behind `IEmployeeFileStore`; writes use a temporary sibling plus atomic rename so final keys never expose partial bytes. Its default root is the git-ignored `App_Data/employee-files` folder, `EmployeeFiles:RootPath` may point to an operator-managed volume, and startup rejects a root equal to or beneath `wwwroot`.
- `Program.cs` owns ASP.NET Core cookie authentication registration, the `/auth/login` and `/auth/logout` endpoints, and the authenticated `/employee-files/profile-photo/{employeeId}`, `/employee-files/documents/{documentId}`, and `/employee-files/documents/{documentId}/preview` read endpoints. Download keeps attachment disposition; preview is inline and accepts only PDF/JPG/PNG validated content types. `EmployeeFileService` applies own-or-elevated authorization before storage is opened.
- `Services/PageAccessService.cs` owns authenticated page access decisions, reads signed-in authorization from the routed `ClaimsPrincipal`, owns principal-only shell access for the signed-in user's own dashboard context, and owns every permission-based elevation beyond that baseline. It also owns the clean-database bootstrap rule for the local `Departments` and `Employees` pages.

- `Services/PersonnelAuthorizationService.cs` is the sole backend authority for target-employee visibility and mutation across common structured personnel pages, bounded employee lookup, Excel operations, and file endpoints. It resolves own-employee, exact department manager/current active delegate, or global-permission scope from persisted organization state plus permission claims. Department responsibility is read-only, excludes bank/identity values, permits education/certificate preview only, and never permits download. `CanManageEmployeeTerminations` remains a separate Management permission. Navbar/button visibility is never the security boundary.

## Data Flow
1. On startup and every local day, `DailyLeaveEntitlementWorker` asks `LeaveBalanceService` to reconcile current-year automatic balances.
2. `LeaveEntitlementService` calculates each active employee's `StartDate`-based eligibility and calendar-day service-tier proration, floors results to whole days, and excludes pregnancy from automation.
3. `LeaveBalanceService` carries previous remaining days only when `CarryOverRule` is enabled, creates missing rows, and updates changed calculated entitlement without duplicating an employee/type/year row.
4. Automatic values above the configured 50-day warning are saved without capping and exposed on `/LeaveCarryOverWarnings` for explicit acknowledgement.
5. An authorized operator may use `/LeaveBalances` for person, department, or all-active-employee assignment; ineligible targets are skipped, and a manual over-limit batch requires one confirmation before any row is saved.
6. An employee selects Annual Leave or an eligible persisted leave type, a date range, and optional half-day; Saturdays, Sundays, and configured public holidays are excluded from the displayed requested-day result. Past dates remain blocked unless the employee explicitly selects the retrospective-request control.
7. Before submission, the form confirms how many working days will be deducted if the request receives final approval, then creates either a normal or explicitly retrospective request through `LeaveRequestService`; both follow the same approval workflow.
8. The request is blocked if its range has no working day, half-day spans more than one date, the employee has no manager, the employee has insufficient balance, or the employee has an overlapping active or approved request.
9. Only the assigned manager approves or rejects the first approval step.
10. Human Resources approves or rejects the final step.
11. Final HR approval adds approved days to used days and creates both persisted source allocations and exact approved date/amount rows; an authorized `/LeaveBalances` correction may also set the current used-day authority and always recalculates remaining days with an audit trail. Annual Leave draws from persisted carry-over allocations first and entitlement allocations second across the three service tiers; Sickness Leave draws from its all-employee balance. Half-day requests deduct and persist `0.5`.
12. Rejection does not change the leave balance and must include a reason.
13. Cross-year leave requests are rejected in Phase 1 so yearly balance semantics stay unambiguous.
14. While a request is still in manager review, its employee can cancel it directly with no balance mutation. Once the manager approves, direct cancellation is blocked until the original HR decision finishes.
15. An approved leave can create a cancellation request with an inclusive start date, end date, and reason; equal dates cancel one day. The assigned manager decides first and HR decides finally. HR approval returns only selected, still-active approval-time day rows to `UsedDays`, records refund provenance, and preserves leave days outside the approved cancellation range regardless of later holiday-calendar changes.
16. `Personel Bilgileri` submits a profile photo for the selected authorized employee; identity, education, and course/certificate dialogs submit a file together with the selected related-record ID.
17. `EmployeeFileService` authorizes the target employee, verifies related-record ownership, validates file content, creates an opaque canonical storage key, atomically writes bytes outside `wwwroot`, then commits metadata and an audit event through a fresh operation context. A failed or cancelled metadata commit performs non-cancelled file compensation.
18. Replacing a profile photo commits the new metadata before removing the superseded file; each new document stores exactly one related-record FK while preserved ambiguous legacy documents retain all-null related-record FKs.
19. Authenticated file endpoints resolve own, exact responsible-department, or global personnel scope before opening the canonical storage key; department responsibility permits preview of education/certificate files only, while download requires own access or the separate global download permission. User-supplied names never participate in path resolution.
